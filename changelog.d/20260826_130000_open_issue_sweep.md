### Added
- `--request-log-max-total-bytes` / `REQUEST_LOG_MAX_TOTAL_BYTES` bounds the request store as a whole. The per-token bound is per token by design — it stops a noisy caller evicting a quiet one's history — but it was documented as "Maximum size of the request log", so a deployment configured for 500 MB with 84 token directories had a 42 GB ceiling that neither the setting nor the docs disclosed. The total cap removes the least recently written token directories first, never the one being written, so the per-token isolation survives (issue #331).
- `logs` decodes stored response bodies before inspecting them. `stream_not_verifiable` was a refusal to decompress rather than a limit: the bytes are ordinary `gzip`, `br`, `deflate` or `zstd` and decode to readable SSE, yet 1163 of ~1600 exchanges on one deployment were declared unknowable — every streamed one among them. All four encodings now round-trip, a stream cut mid-flight still yields the frames that arrived, and a stale `complete: false` stamped on an unchecked stream is corrected by what the bytes actually say. Only an encoding the router genuinely cannot decode stays unverifiable (issue #328).

### Security
- The proxy no longer forwards the caller's machine identity to the vendor. It hid the client's IP while relaying `x-stainless-os`/`-arch`/`-runtime`, the client `user-agent`, `accept-language` and `x-claude-code-session-id` unchanged, so a deployment on Linux reported a developer's `MacOS`/`arm64` laptop and a stable session id correlated requests across tokens. Upstream headers are now an allowlist — the shape the git and GitHub proxies already used — with a normalised `user-agent` naming the deployment, so one deployment presents one identity and a header nobody considered is dropped rather than disclosed (issue #332).
- The GitHub policy denies destructive operations by effect, not by HTTP method. `PUT` to branch protection or a repository ruleset, `POST` to repository transfer, and a `PATCH` carrying `archived`, `private`, `visibility` or `default_branch` were all allowed while the `DELETE` beside each one was denied — and `PUT .../branches/{branch}/protection` replaces the whole protection object, reaching the same end state as the refused deletion. The GraphQL surface denies the same effects, so the two spellings of one API cannot disagree. Configured rules are still evaluated first, so one allow rule remains the escape hatch (issue #329).

### Fixed
- `request_log` lines name the model the request asked for. The field was present in the format and never populated: it was read from a response header the router sets only when the upstream substitutes a different model, so every ordinary line — success and failure alike — said `model=-` while the body sat in the middleware's own buffer. `-` now means a request that genuinely has no model (issue #320).
- `with` says nothing of its own on the ordinary interactive path. A bare launch was silent while any client flag earned two `note:` lines above the client's own banner, so advice arrived in inverse proportion to how much the user needed it. Refusals, a mode that could not be applied, and a choice the router made on the user's behalf still explain themselves (issue #330).
- `tls --help` lists only options that can change what `tls` does, instead of the twenty serve-only ones (`--port`, `--upstream-base-url`, `--routing-mode` and the rest) that cannot — the same treatment issue #312 gave `with`. The refusal shown when `tls` is aimed at a remote deployment no longer runs its words together (issue #308).
