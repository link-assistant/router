# In-memory owned API adoption sequence

`proposeSourceBackedCoreAdoptionSequence` composes the actual source-backed
formatting, literal-matches and vector corpus APIs, in that order. The existing
APIs, conservative barriers and output schemas remain unchanged. The sequence
uses the fixed language/repository rule phases; its three source steps are
suboperations, not additional translation phases.

Every step receives the complete preceding after-map. Its actual corpus API
creates a fresh module graph and private attribute/source inspection. The
sequence independently rejoins complete input rows, current module edges,
diagnostics, physical module origins, source-view digests, file CSTs and edits.
Original coordinates are never borrowed after an earlier length change.

The result retains the complete original and final Rust maps, every complete
step proposal and both directions of each source substitution. A per-invocation
document inventory stores a full source and serialized/reparsed Rust CST for
each distinct path/content pair. Original, intermediate and final inventories
reference those complete documents, including unchanged files. Sharing those
DATA strings within this one invocation grants no source or semantic permission;
there is no across-invocation cache. The existing packet source/document quotas
are reused. An external artifact writer must still enforce its complete logical,
stored and aggregate evidence bounds.

`reviewSourceBackedCoreAdoptionSequence` reads detached DATA. It independently
reconstructs all source maps and current module graphs, checks complete CST
documents, hashes, file edits, inverse partitions and phase order, and reverses
every step back to the exact original maps. It issues no parser, namespace,
attribute or executable owner identity.

For function accounting, each selected current function must join its actual
complete source item. Earlier file mappings translate both boundaries back to
one exact original path/module/name/span and body hash. Groups retain every
selecting step. `candidateSelections` is separate from
`distinctCandidateFunctions`; neither is a coverage gain. Current mixed-family
barriers can leave a function unchanged through all three steps. The sequence
does not relax those barriers to obtain more candidates.

Complete manifest and lock strings are mandatory for this new Router sequence.
They are freshly joined through the existing genuine dependency issuer even
when a corpus has no derive. Each actual adopter receives those same complete
strings; any retained producer dependency input must agree. Inputs outside that
issuer's audited domain remain outside this initial sequence. Existing standalone
corpus APIs retain their broader DATA-only input contracts.

`proposePhysicalCoreAdoptionSequence` reuses the shipped physical source-tree
snapshot and Cargo reader. It reads the complete production `src` tree and the
actual package manifest, workspace manifest where present, and lock. A final
source census/identity/content rejoin and complete Cargo rejoin precede returning
the proposal. `reviewPhysicalCoreAdoptionSequence` independently repeats those
physical joins around detached DATA review. Neither API installs edited sources
or writes proposal files.

The physical wrapper's domain is the complete production source tree. It does
not claim to capture all tracked tests, benches or other Rust outside that tree.
A whole-project evaluator must retain those additional original sources and its
compiler/native-source freeze, overlay the returned final production map in
memory, and freshly check the complete before and after projects. Cargo byte and
audited-profile joins also do not establish every actual Cargo unit, invocation
flag or feature selection.

The seven complete receiving cases cover three real steps, changed coordinates,
the final genuine project with JS/strict TypeScript witnesses, exact source/CST
inverses, duplicate/count/source/Cargo corruption controls, mixed/unknown producer
barriers, ambiguous physical module aliases, complete physical Cargo retention,
source additions and changes, and linked roots. These tests remain unrun in this
source-only draft. No Rust tool or application source installation was performed.

The result reports `semanticAdmission: false`, `executableCoverageGain: null` and
`applicationSourcesInstalled: false`. A source inverse is fidelity, not reverse
executable coverage. The earlier complete whole-project attempt stopped at its
900-second cap before a finished admission result; this composition draft does
not fill that production measurement gap.
