# Owned module source restoration draft

`restoreOwnedModuleProject` adds a draft inverse from canonical packaged Rust
to the actual original JavaScript or TypeScript module tree. It rebuilds the
original native export and declaration bindings from current source bytes on
every call. It accepts no saved module history or source verdict as authority.

The language sequence checks the full edited Rust through the existing private
owned issuer, serializes and reparses checked meta, and requires complete inner
and outer Rust reproduction. Native symbols then select function references,
runtime imports and written type imports for redistribution. Existing functions
return to their original modules and local names. Newly checked functions go to
the entry module; removed functions disappear from its reconstructed bodies.
Public aliases come from the actual checked Rust envelope. Empty imports retain
the declared pure-module census when a module loses its final function.

The receiving linker is a complete source copy of the existing owned linker,
with separately declared language and repository substitutions. Identifier
proposals select actual declarations and preserve linked native names; they
grant no type, ownership or execution authority. Every reconstructed tree
enters a new private checker, and its full emitted Rust must reproduce the
authoritative input again. Changes outside that canonical representable order
refuse; there is no fallback to saved bodies or unchecked replacement code.

Repository rules retain every complete original module, its native selections,
lossless CST equation and inverse. Runtime/library internals remain behind
their existing explicitly checked boundaries. The original whole-source byte,
file, statement and native traversal bounds remain in place. There is no new
cross-invocation cache, native execution or parity claim.

Independent JavaScript execution, TypeScript restoration, source-conflict,
unknown-effect, accessor/proxy and source-copy regression cases are drafted.
They have not run. Multi-module transaction integration, broader syntax and
production coverage remain open; this family does not complete issue #759.
