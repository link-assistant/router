# Actual standard filesystem composition: source draft

All implementation, receiving cases and native oracle source remain unrun.
The resource caller lane now composes eighteen original std/tokio filesystem
string-path operations with its existing text, ownership, branch, loop and
resource rules. The matching original OS adapter remains intact. Every imported
operation is independently reissued through the complete original filesystem
translator, its Rust semantic checker and serialized/reparsed checked program.
Table membership, path spelling and public result records cannot supply that
qualification; an unresolved original namespace still refuses.

I/O Results have a distinct structured error family and emit the actual
`::std::io::Error` type. Error propagation cannot flatten it into a text or
control error. Full original Result guards retain cleanup and complete outcome
checks. Standard paths remain fully qualified. Captured capabilities retain
the original runtime's invocation scope, OS behavior, NUL handling and adapter
fault boundaries.

Filesystem async operations return eager Promises. A caller must place them
inside an actual deferred async body and immediately await each operation.
Direct eager async tails refuse; an async table field cannot supply Rust's
cold polling behavior. Native inverse proposals reconstruct this wrapper and
still require fresh whole JavaScript checking and complete Rust reproduction.

A separate additive runtime closure installs the matching filesystem declaration
source for receiving targets and source units without changing the older
deadline source APIs. Actual imports require complete current runtime and
declaration bytes. Independent unrun JS/strict TS/native source covers Unicode,
ordering, deferred polling, complete I/O failures, remaining operation signatures,
NUL paths, error-family mixing, declaration changes and forged meta.

Full originals retain native-selected spans, ordered language then repository
substitutions, serialized/reparsed lossless CST and complete inverses. Byte
vectors, additional filesystem handle/metadata APIs, generic capabilities,
namespace/bootstrap, production adoption, runtime parity and every unfinished
ledger requirement remain open.
