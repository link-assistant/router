# OAuth Durability and Subscription Health Design

**Date:** 2026-09-01

**Scope:** GitHub issues #382, #383, #384, and #385, delivered in one pull
request and one patch release. If the release fails, repair it through a focused
follow-up pull request and repeat delivery verification.

## Context

Router v0.125.2 has one shared OAuth refresh ladder, but not every caller
registers a credential store and the ladder deliberately fails open when its
lock or write cannot be used. A rotating refresh-token endpoint can therefore
consume the only valid chain link without leaving a durable replacement.

The subscription health endpoint has a separate evidence error: production
constructs a reader for every supported provider, then treats reader presence
as credential presence. Missing Gemini and Qwen homes can consequently appear
healthy on a deployment that mounted only Claude and Codex.

Provisioning has the same transaction-boundary gap. `auth import` probes a
candidate and then unconditionally replaces the vendor document without the
refresh-recovery lock. An orchestrator cannot express "install only if this
deployment is still empty": checking first races with interactive login and
refresh, and can move a newly rotated chain backward.

The delivery establishes three explicit boundaries:

- every refresh is a locked durable transaction, regardless of whether it was
  triggered by serving, catalog discovery, `auth status`, or `doctor`;
- provider health is derived from credential and live-discovery evidence, not
  from the set of reader objects the binary knows how to construct;
- every Router-owned credential writer shares the provider/account lock and
  the owner-only atomic installation primitive.

## Chosen architecture

### Recoverable credential-store decorator

Add a `RecoverableCredentialStore` around each `SubscriptionReader`. The
decorator is scoped by provider and account and rooted in the router's writable
`data_dir`. It implements the existing `CredentialStore` interface, so the
refresh ladder, account pools, and vendor-CLI recovery retain one policy path.

The decorator owns two owner-only files below a `refresh-recovery` directory:

- an advisory lock shared by every process for that provider/account;
- an atomically replaced recovery record containing a normalized fresh token
  and a fingerprint of the primary chain link it supersedes.

The account portion of each filename is SHA-256-derived rather than copied into
the path. Recovery records include a version and provider and are validated on
read. Token values are never logged or included in public health responses.

The data-directory lock is intentional. A read-only vendor mount cannot create
a sibling lock, but a writable `data_dir` can still serialize every router and
diagnostic process and can durably preserve a rotation when the primary mount
cannot be updated.

### Recovery and reconciliation algorithm

Before an exchange, the ladder must acquire the registered store's lock. A
missing store, missing lock path, open error, or timeout is a refresh failure;
the token endpoint receives zero requests. The old credential may still be
probed by the caller, but no refresh is claimed.

While holding the lock, `reload` reads both the primary credential and any
recovery record:

1. If the primary equals the recovered token, remove the completed recovery
   record and return the primary.
2. If the primary differs from the recorded baseline and recovered token, an
   operator or another holder installed a new chain. Remove the stale recovery
   record and return the new primary.
3. Otherwise the recovery token is authoritative. Attempt to reconcile it into
   the primary store; remove the record only after that write is durable.
4. If reconciliation still cannot write the primary, return the durable
   recovery token so the process never replays the stale file.

After a successful token exchange that rotates the refresh link, persistence
must complete before the fresh token can leave the ladder. The decorator first
tries the vendor file and, on failure, atomically writes the recovery record.
If both destinations fail, the ladder returns a storage error and does not
cache or report the fresh access token as safe. An unchanged refresh link needs
no token-document write, but still runs under the same lock.

Atomic replacement plus file and directory synchronization keeps the previous
credential or recovery record readable across interruption. Recovery-file
removal also synchronizes the containing directory.

### One registration path for every caller

Add a shared `TokenCache` registration helper that decorates readers with
`data_dir` recovery before inserting them. Use it for:

- the serving `AppState`, including every account-pool reader;
- local `auth status`;
- `doctor::subscription_catalog_diagnostics`.

Catalog refresh may register a raw reader only when no store is registered; it
must never replace a recoverable store already installed by the serving path.
Diagnostic commands also persist rejection evidence in the same `data_dir`.

`auth status` will return a non-zero exit when its refresh transaction records
a lock or durability error. It must never print `usable` after a rotation that
could not be made durable. `doctor` already returns a failure boolean and will
include the same refresh error in that result.

### One locked credential-installation boundary

Factor the hashed data-directory lock-path derivation out of the recovery-store
decorator so refresh, import, native Claude/Codex login, and the admin login API
resolve the same `provider` + `account` lock. Router-owned writers acquire that
lock before re-reading or replacing a vendor document and install through the
same owner-only atomic, file-and-directory-synchronized primitive.

Add `auth import ... --if-absent` for Claude, Codex, Gemini, and Qwen. Import
still parses the source document and probes its normalized credential before it
can change the destination. After acquiring the shared lock it re-checks every
destination filename that the reader recognizes:

- when any credential is present, return a distinct successful `already
  present` outcome without changing its bytes, digest, or timestamps;
- when the destination remains absent, install the original vendor document at
  the provider's canonical path atomically;
- when the candidate is malformed, fail before the lock/write phase;
- when the vendor explicitly rejects the candidate, conditional import refuses
  to install unless the operator also supplies an explicit force option;
- an unreachable probe remains `unverified` rather than falsely rejected.

Ordinary import remains the explicit replacement operation, but now uses the
same lock and atomic installer. `--force` controls adoption of an explicitly
vendor-rejected candidate; it never changes `--if-absent` into overwrite.
GitHub credential import is outside this subscription-credential operation and
retains its existing behavior.

Native login exchanges happen before the lock; only credential installation is
serialized. The CLI and `LoginManager`/admin endpoint pass the resolved
`data_dir` into their Claude and Codex authorization configurations. Holding the
same lock means a refresh and conditional import cannot cross writes or move a
chain backward. Lock open/acquisition/timeout failures leave the destination
unchanged and are operator-visible.

### Explicit provider health states

Replace the boolean-only provider verdict with an explicit state:

- **absent:** `SubscriptionError::NoCredentials`; omit the provider entirely;
- **starting:** a readable credential exists, but no live catalog has completed;
- **healthy:** live discovery succeeded and current evidence is not rejected;
- **degraded:** a credential file exists but is unreadable/malformed, or live
  evidence says the configured credential cannot serve.

`/health/subscriptions` retains `healthy_providers` and
`degraded_providers`, and adds `starting_providers`. Starting is HTTP 200 and
does not trigger the degraded status; it is not mislabeled healthy. Any
degraded provider produces HTTP 503. Public reasons remain fixed summaries and
never expose credential paths or upstream response bodies.

`/v1/models` and metrics consume the same state. After discovery, a provider is
healthy exactly when it can contribute its owned live models; an absent reader
cannot appear in health or model ownership. The Prometheus compatibility gauge
stays `1` for starting and healthy and becomes `0` only for degraded, avoiding
a cold-start alert while the JSON endpoint preserves the distinction.

## Alternatives rejected

Putting fallback persistence into `SubscriptionReader` would couple a
vendor-file adapter to router-wide data paths and make non-reader stores behave
differently. Journaling only inside `TokenCache` would duplicate persistence
policy outside `CredentialStore` and leave vendor-CLI and future callers able
to bypass it. Continuing unlocked or in memory preserves availability for one
process by guaranteeing failure after restart and is the behavior these issues
remove.

## Testing

All production changes follow red-green TDD. The refresh matrix covers Claude,
Codex, Gemini, and Qwen vendor layouts and proves:

- rotated tokens survive restart and preserve vendor-specific fields;
- two independent caches serialize to one exchange;
- lock timeout/error produces no endpoint request;
- primary-write failure lands in recovery and is reconciled by a fresh cache;
- failure of both durable stores does not return/cache the fresh token;
- interrupted primary and recovery writes leave readable state;
- `auth status` and doctor construct the same registered cache as serving.

Conditional-import tests cover all four vendor layouts and prove an empty
destination installs the original document, an existing destination remains
byte-for-byte identical, a destination created while the importer waits for the
lock wins, refresh and import serialize on the same path, malformed/rejected
candidates do not change the destination, and atomic replacement never exposes
a partial document. Native CLI/admin login tests assert their install path uses
that same lock.

Health tests cover only Codex, Claude plus Codex, absent Gemini/Qwen readers,
malformed and unreadable files, starting state, rejection, and agreement with
discovered model ownership.

The final gate includes formatting, check, Clippy with warnings denied, the
full test suite, coverage, audits, package/release scripts, changelog validation,
and independent code review. Before merge, refresh the issue list and ensure
the single PR closes #382, #383, #384, and #385. After merge, verify the patch
release, GitHub assets, crates.io, GHCR, Docker Hub, multi-platform manifests,
