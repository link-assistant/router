# Security review — August 2026 (issue [#52](https://github.com/link-assistant/router/issues/52))

> Historical route inventory: this review records the HTTP paths that existed
> at the reviewed commit. Router 1.0.0 removed those aliases; use the
> [canonical route migration](../migrations/1.0.0-canonical-routes.md) for the
> current surface.

A deliberate review pass over the surface added by
[#47](https://github.com/link-assistant/router/issues/47) (REST login API driving
the Claude CLI on a PTY),
[#49](https://github.com/link-assistant/router/issues/49) (scoped admin JWTs),
[#50](https://github.com/link-assistant/router/issues/50) (React admin console
with a two-phase bootstrap claim) and
[#51](https://github.com/link-assistant/router/issues/51) (Telegram/VK admin
bots).

This document records **everything that was checked, including what was found to
be fine** — a review whose only output is a list of fixes cannot be re-read later
to see what it did *not* cover.

## Threat model

The router holds a credential to a **paid** account. Compromise costs money
directly, not just data.

The realistic adversary is **anyone who can reach an exposed port**, including
someone who finds the deployment *before its owner completes the first-run
claim*. Concretely:

| Adversary | Reaches | Wants |
| --- | --- | --- |
| Internet scanner | proxy port (`--port`, commonly public) | free inference on the operator's paid account; the upstream credential itself |
| Same adversary, admin port exposed by misconfiguration | admin port (`--admin-port`, default host `127.0.0.1`) | to win the bootstrap claim first and own the router |
| A stranger who messages the bot | Telegram/VK bot | the same claim, through a channel the web UI never observed |
| A malicious page in the operator's browser | the operator's session | the admin token in `localStorage`; a framed click on *revoke*/*rotate* |
| Anyone who can read logs, transcripts or `doctor` output | disk / stdout | credentials printed in passing |

Out of scope (unchanged by #47–#51 and assumed): an adversary with local
filesystem access to `--data-dir`, or the ability to restart the process with a
different `--data-dir`. Such an adversary already owns the deployment.

## Findings and fixes

Four issues were found and fixed in this pass, each with a regression test.

### F1 — the admin listener sent no security headers

The console keeps the admin credential in `localStorage` (a documented trade-off
of #50), and its state-changing actions — revoke, rotate — are one click. With no
`Content-Security-Policy` there was no containment for an injected script that
reads that key, and with no `X-Frame-Options` the console could be framed and
clickjacked.

Fixed by `src/security_headers.rs`, applied as the **outermost** layer of the
admin router so it also covers the auth middleware's own refusals and the
embedded UI assets: `frame-ancestors 'none'`, `script-src 'self'`,
`form-action 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer`. `style-src` must keep `'unsafe-inline'` because
emotion (Chakra UI v3) injects `<style>` at runtime; this is recorded here as a
known, accepted weakening rather than left silent.

Regression: `every_admin_response_is_hardened` in `tests/security_review_test.rs`.

### F2 — the paid-account credential could be returned in a login error

`SUCCESS_MARKERS` in the login flow contains `"sk-ant-oat"` — proof that the
credential *appears in the PTY transcript*. That transcript's tail was quoted
verbatim into the login API's error strings, so a login that failed *after* the
token was printed handed the token to the caller.

Fixed by `login_url::redact_secrets` (prefix-driven: `sk-ant-`, the router's own
`TOKEN_PREFIX` and `ADMIN_TOKEN_PREFIX`) and `login_url::redact_value` (the
authorization code the human pasted, which the terminal echoes and which no
pattern can recognise). Redaction runs **before** truncation, so a length limit
cannot leave a usable prefix behind.

Regressions: `a_printed_credential_never_survives_redaction`,
`the_routers_own_credentials_are_redacted_whole` in `src/login_url.rs`;
`a_failure_excerpt_carries_neither_the_token_nor_the_pasted_code` in
`src/login.rs`.

### F3 — the session registries were unbounded

`LoginManager` never removed terminal sessions, and `ChatAdmin.sessions` was
keyed by an **unauthenticated** platform user id and never removed anyone — so
any stranger who could message the bot could grow it without limit.

Fixed: login sessions record `settled_at` and are evicted after a 300 s retention
window (long enough for the client to read the result); expiry now also drops the
PTY, which kills the child process. Chat sessions are pruned on every message
(1 h idle TTL, 512-entry cap, evicting credential-less strangers before
authenticated conversations, and never the current one).

Regressions: `finished_sessions_are_evicted_once_their_result_has_been_retained`,
`an_expired_session_becomes_evictable`,
`a_flood_of_strangers_cannot_grow_the_session_map_without_bound`,
`the_active_conversation_survives_the_cap`.

### F4 — disclosing read endpoints were open on the network-facing port

`ENABLE_METRICS` defaults to `true` (`src/config.rs:346`), which mounted
`/v1/usage` and `/v1/accounts` on the **proxy** port. `/v1/usage` names token ids
and labels; `/v1/accounts` names credential filesystem paths. Both answered
unauthenticated callers.

Fixed: both handlers now require `is_admin_authorised` (admin-scoped JWT, the
flat `TOKEN_ADMIN_KEY`, or — on the admin port, where the same handlers are
mounted as `/api/admin/usage` and `/api/admin/accounts` — the claimed
credential). `/metrics` is **deliberately left open**: it is aggregate counters
only and scrapers are unauthenticated by convention.

Regression: `the_disclosing_read_endpoints_require_admin_but_metrics_stays_scrapable`.

## Checklist — what was examined

### Bootstrap claim (#50, #51)

- **Won twice, or through a channel that did not observe another's claim?** No.
  The web UI and both bots hold one `Arc<AdminClaim>`; only one candidate is
  outstanding at a time and only `confirm` closes bootstrap. Pinned by
  `the_bootstrap_claim_can_be_won_only_once_across_channels`, which wins the
  claim *in chat* and then asserts HTTP `/api/admin/bootstrap` returns 409 and a
  second chat user is handed nothing.
- **Restart between mint and confirm?** The candidate lives in memory only —
  nothing is persisted until confirm — so a restart discards it and leaves the
  system unclaimed and re-mintable. Correct: it fails towards "claimable", never
  towards "silently claimed".
- **Unconfirmed candidate replayed or used before confirmation?** No. A minted
  candidate authorises nothing; `verify` matches only the *active* credential.
- **Abandoned claim → permanently unadministrable, or permanently claimable?**
  Neither permanently: the candidate expires after `--admin-claim-ttl-secs`
  (default 120 s) and the mint is retryable. It does stay claimable until someone
  claims it — that is the intended first-run design, and it is exactly why the
  threat model above names "someone who finds the deployment before its owner".
  Operators who cannot accept that window should set `TOKEN_ADMIN_KEY`, which
  closes bootstrap from the start.
- **Resettable by someone who can restart the container?** Yes, by deleting
  `<data-dir>/admin-claim.json`. Accepted: that requires filesystem access to the
  data directory, which is out of scope above.
- **Persistence:** only the SHA-256 digest of the active credential is written.

### Admin credential (#49)

- **Scope enforced on every admin route?** `require_admin` in `src/admin_api.rs`
  is a router-wide middleware with an explicit three-entry allow-list
  (`/api/admin/status`, `/api/admin/bootstrap`, `/api/admin/bootstrap/confirm`) —
  a new route is protected by default rather than by remembering to guard it.
- **Can a client token be accepted where an admin token is required?** No, on
  either port. Pinned by
  `a_client_token_is_refused_where_an_admin_credential_is_required` and by
  `ordinary_client_token_is_rejected` in `src/admin_auth.rs`.
- **Constant-time comparison?** Yes: `token::constant_time_eq` (`src/token.rs:344`)
  and `admin.rs:398`, both length-safe.
- **Rotation invalidates the predecessor / revoking the token in use?** Yes —
  only one digest is stored, so rotation replaces it. Chat sessions re-validate
  their stored credential on **every** command, so a revoked or rotated
  credential stops working immediately rather than at the next session boundary.

### Login sessions (#47)

- **Unbounded process/PTY growth?** Was a real gap; fixed in F3.
- **`login_id` guessing/enumeration?** `login_id` is a v4 UUID
  (`src/login.rs:269`) — 122 bits of randomness, not a counter.
- **Credential leaking into logs, transcripts, captured frames?** Was a real gap;
  fixed in F2.
- **Cleanup on expiry, failure, shutdown?** Expiry now drops the PTY (killing the
  child); terminal sessions are evicted after the retention window; process exit
  drops the manager and with it every PTY.

### Web UI (#50)

- **XSS reaching the `localStorage` token?** Contained by the CSP added in F1;
  React escapes interpolated text by default and the console has no
  `dangerouslySetInnerHTML`.
- **CSRF on state-changing admin routes?** Not applicable: authentication is a
  `Bearer` header, not a cookie, so a cross-site form or image cannot carry it,
  and no CORS layer is installed (the `cors` feature is enabled in `Cargo.toml`
  but unused), so a cross-origin `fetch` cannot read the response either.
- **Clickjacking?** Fixed in F1 (`frame-ancestors 'none'` + `X-Frame-Options`).
- **Admin port reachable from the proxy port or vice versa?** They are separate
  listeners with separate routers and separate bind addresses; the admin listener
  does not exist unless `--admin-port` is given, and defaults to `127.0.0.1`.
- **Rendering of server-controlled strings?** Token labels and error strings are
  rendered as React text nodes.

### Chat bots (#51)

- **Private-chat enforcement trickable by forwarded or edited messages?** No.
  Telegram long polling requests `allowed_updates: ["message"]`, so
  `edited_message` updates never arrive at all; non-private chats, bot senders
  and senderless messages are dropped. VK requires
  `peer_id == from_id && from_id > 0 && peer_id < CHAT_PEER_OFFSET`, which is the
  1:1-conversation condition.
- **Platform user id sufficient on its own?** No — it only keys a session; every
  privileged action requires the credential the user pasted, re-validated per
  command.
- **Rate limiting on the JWT prompt?** The prompt itself is not rate limited, but
  a wrong token yields no distinguishing signal and the session map is now
  bounded (F3), so the remaining cost of a flood is bot-API-side. Noted as a
  residual, accepted risk rather than fixed.
- **Tokens in message history?** Unavoidable for a paste-based flow and inherent
  to the design: the candidate token is *shown* in chat by construction. This is
  why chat credentials are revocable and rotation invalidates the predecessor.

### Cross-cutting

- **Secrets in logs at every verbosity (`RUST_LOG=trace`)?** No `trace!`/`debug!`
  site logs a header, token or key value; the one credential-adjacent `debug!`
  (`src/oauth.rs:198`) prints a path and expiry timestamps only. The audit log
  records `token_id` (the JWT `sub`) and label, never the token
  (`src/audit.rs:25`).
- **`doctor` output?** Prints `admin_key: set/<unset>`, `admin_ui: enabled/…` and
  `admin_credential: provisioned|claimed|UNCLAIMED` — states, never values
  (`src/main.rs:805-838`).
- **Token values re-displayed?** No. Issued tokens are shown exactly once; only
  digests are persisted.
- **Error messages over-distinguishing "wrong token" vs "no such token"?** The
  admin port answers a single `authentication_error` / "admin credential
  required" for every failure mode.
- **`cargo audit` and the JS toolchain?** Added as a dedicated `audit` job in
  `.github/workflows/release.yml` running `cargo audit` and `npm audit
  --audit-level=high` in `ui/`. It deliberately does **not** gate `build`: an
  advisory can be published against an unchanged tree, and that should raise a
  red check rather than block an unrelated release.

  Running it for the first time found one real advisory —
  [RUSTSEC-2026-0185](https://rustsec.org/advisories/RUSTSEC-2026-0185), remote
  memory exhaustion in `quinn-proto` (7.5 high) — fixed here by updating
  `Cargo.lock` to `quinn-proto` 0.11.16. `npm audit` over `ui/` reports zero
  vulnerabilities. One advisory is consciously ignored in `.cargo/audit.toml`:
  [RUSTSEC-2023-0071](https://rustsec.org/advisories/RUSTSEC-2023-0071) (Marvin
  Attack in `rsa` 0.9) has no fixed release upstream and reaches us only through
  `jsonwebtoken`'s RS\*/PS\* support — this router signs and verifies with HMAC
  (`Header::default()` / `Validation::default()`, i.e. HS256, `src/token.rs:182`)
  and never performs an RSA private-key operation, so the vulnerable path is not
  reached. Each ignore in that file carries its justification inline.

## Residual, accepted risks

1. The first-run claim window: until someone claims it, whoever reaches the admin
   port first becomes the administrator. Mitigate with `TOKEN_ADMIN_KEY` or by
   keeping the admin port on loopback (the default).
2. `style-src 'unsafe-inline'`, required by emotion's runtime style injection.
3. The admin token lives in `localStorage`, so any script execution on the admin
   origin can read it. The CSP is the containment; there is no HttpOnly-cookie
   alternative without adding CSRF surface.
4. Candidate tokens appear in chat message history by construction.
5. Anyone with write access to `--data-dir` can reset the claim.
