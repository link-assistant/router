# JavaScript gates expose Router's remaining work

Router should make native JavaScript behavior, strict feature parity and deterministic translation the prerequisite for expensive Rust verification. The evidence supports that design, but **does not establish a complete native JavaScript Router or a completed conversion**. Retained histories contain **4,184 workflow runs** across the four comparison branches; Router reached four revisions with all seven observed workflows green, while meta-language's principal CI and formal-ai's principal pipeline never succeeded in the captured history. Relative-meta-logic's **92/92 green parity runs alongside 0/23 green acceptance runs** demonstrate why a parity badge cannot substitute for a complete requirements gate. Router's observed failures include coverage policy, a missing changelog fragment, registry rate limits and a timing-sensitive test, so changing languages cannot correct every cause. The reported host incident additionally separates compiler cgroup kills, host Docker-daemon OOM and recovery-copy disk exhaustion. This case study preserves those distinctions, identifies a genuine bounded Rust → intermediate representation → JavaScript path, and records the remaining work against every requirement of [issue #759](https://github.com/link-assistant/router/issues/759). ([Computed retained-history metrics](raw/ci/computed-metrics.json), [PR #749](https://github.com/link-assistant/router/pull/749), [relative-meta-logic #184](https://github.com/link-foundation/relative-meta-logic/pull/184))

## Distinct failures require distinct corrections

Router's failures establish several causes beyond compiler load. A missing release fragment directly failed the changelog check in run `37862094392`. Coverage in run `37873145649` measured **86.50% against an 86.76% default-branch baseline**. Later runs could exceed measured coverage yet still fail the separate policy requiring a committed, reviewable baseline increase: the experiment notes for run `38007252770` report 80,586 covered of 92,490 measured lines, or 87.129419%, while the failed job asks for that baseline update. ## A typed portable core gives translation an honest boundary

The strongest demonstrated **explicit Rust → meta → JavaScript path for a bounded pure fragment** is formal-ai's JavaScript-hosted Rust frontend, `portable-pure-v1` intermediate representation in Links Notation, and JavaScript emitter. `parseRustItem(tokens)` handles bounded typed functions/constants and refuses unsupported generic functions, methods, statements, macros and literals. The CLI exposes `--to meta`, `--from meta --to rust`, and reversible JavaScript/Rust translation through shared frontend/emitter modules. Its baseline JavaScript backend emits **JSDoc, not typed TypeScript**. A typed TypeScript emitter is a new adapter to implement and validate, rather than an existing capability to claim. For the CI dependency, prefer one triggering workflow with a reusable JavaScript prerequisite and `needs` from all Rust paths, using the prerequisite's exact tested SHA for downstream checkout. Separate `workflow_run` designs require explicit upstream conclusion, source `head_sha`, repository/event and trust checks because the downstream event's ordinary SHA identifies the default branch and the run can receive privileged tokens. Path filters must not skip strict parity/regeneration. ([GitHub `needs` contract](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds), [`workflow_run` semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), [workflow template](standard/workflow.template.yml))

Publication should use a shared writer concurrency group with **`cancel-in-progress: false`**, preserving release/deploy/tag writes. Do not set a workflow-level active-cancellation policy around a started Rust stage or writer. GitHub still replaces a pending run by default even when active cancellation is disabled, so the one-owner, no-push-during-current-CI policy remains meaningful. Cache sharing requires compatible toolchain, flags, features, profiles and targets; a common target directory cannot remove incompatible rebuilds. Cargo supports a shared target and documents sccache as another dependency-cache option, but neither establishes a measured saving in this task. ([GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [Cargo build-cache contract](https://doc.rust-lang.org/cargo/reference/build-cache.html))

The [reusable standard](standard/README.md) includes agent/contribution templates, a strict inventory checker with tiny synthetic fixtures and a callable workflow contract. It is a starting point for adopting repositories, not evidence of their runtime parity. Its placeholders must become checked-in repository commands; complete inventory must be paired with shared behavior tests and forward/reverse generation checks. Adoption is complete only when deliberate native-test failure, missing/partial/carried feature, generated drift and skipped prerequisite each prevent every expensive downstream path, while a complete unchanged candidate passes at the exact tested revision. Release writer tests must additionally show that superseded read-only verification cannot cancel an active writer.

The decisive next milestone is a single reviewed candidate that passes the **complete strict gate**, backed by a complete feature inventory and executable shared observations. Until then, preserving a visible blocked readiness result is useful progress: it tells the publication owner exactly which implementation contracts still need work. After that milestone, a controlled typical-feature experiment can answer whether the workflow reduces CI cycles, local memory and disk use. The existing retained-history and provenance bundle makes that comparison possible without treating a policy change, a reversible envelope or an incomplete measurement as the promised outcome.
